# Submission-record error and warning coverage

This inventory was made before revising `ambry-record-warning-cases.xlsx`.
It covers the current record-validation messages and visible record warnings,
not every spelling of invalid input or unrelated upload/system failures.
All rows are artificial UI test data for Ambry Genetics (GENCC:000101), not
curated gene–disease assertions. Do not publish them.

## Workbook layout and use

There are **20 submission rows total in two files**:

- `ambry-record-warning-cases.xlsx` contains 14 uploadable record cases: 8
  current-data cases followed by 6 fixture-dependent cases.
- `ambry-record-warning-cases-upload-blocked.xlsx` contains 6 cases rejected
  before individual records can be created.

Each file has exactly one worksheet, uses the normal 18 columns, has headers on
row 6 and data starting on row 13. The application imports only the first
worksheet, so separate files are required for these two upload paths.

Use a clean local test context. Re-uploading accepted rows can itself produce
duplicate errors. The main sheet uses distinct gene/original-disease/MOI tuples;
existing records in the receiving database can still affect duplicate checks.
The local database currently contains no live unpublished Ambry submission,
so F14 cannot demonstrate its warning without a prerequisite fixture.

No fixture is installed by this workbook or its builder. No database changes,
API submissions, publishing, or commits are part of preparing this artifact.
The synthetic identifiers below must be checked for collisions before any
future fixture setup, and must only be used in an isolated local test database.

## Prerequisites for F09–F14

The six fixture rows can coexist with the following setup:

- MONDO:9999001: active, label `Fixture candidate A`, exact OMIM:999901.
- MONDO:9999002: deprecated, label `Fixture candidate B`, exact OMIM:999901.
- MONDO:9999003: active, label `Fixture bridge target`, exact OMIM:999902,
  OMIM:999903 and OMIM:999904.
- Orphanet:999902: exact MONDO:9999001 and MONDO:9999002; exact OMIM:999902.
  No MONDO term exact-matches Orphanet:999902.
- Orphanet:999903: no MONDO equivalents; exact OMIM:999901 and OMIM:999903.
  No MONDO term exact-matches Orphanet:999903.
- No original row for OMIM:999904. This is deliberate for F12.
- MONDO:9999004: deprecated, replaced_by MONDO:9999005; that replacement is absent.
- For F14, a live unpublished Ambry submission matching HGNC:5,
  original disease MONDO:0007947 and HP:0000007, with no blocking duplicate.
  For the alternate blocking case, use a pending or live published duplicate
  instead. That alternate state changes the expectation for the same row.

F09 should name candidates 9999001 and 9999002. F10 should name those same two
and **not** 9999003. F11 should name all three. Without these fixtures, F09–F13
normally yield ordinary missing-mapping errors, not their intended scenarios.

## Limits discovered while identifying the cases

- Spreadsheet validation rejects missing/invalid fields and dates before
  creating records. For B15–B20, the workbook documents both the upload result
  and the corresponding raw-record behavior; it does not bypass validation.
  For B15's raw API variant, omit the missing fields or use null (not empty
  strings). The spreadsheet blanks themselves are rejected before that stage.
- `DocumentController::process_pmids()` normalizes PMIDs before
  `Submission::load_from_json()` receives them. R08's six issues therefore
  appear in file validation but are lost before persistent record warnings are
  created. This is a coverage limitation, not a change made by this fixture.
- `criteria_url` is initialized as an error for a blank UI record, but is not
  validated by `load_from_json()`. B15 includes an empty criteria URL to show
  the upload requirement; reproducing the initial record marker requires a
  blank UI record. Mechanism validation is disabled, and publish-date editing
  is commented out: there are no active uploaded-record cases for them.
- Short numeric PMIDs produce a log warning only. Duplicate PMIDs and accepted
  PMID prefixes/suffixes are normalized without persistent issue entries.
  They are not separate visible record warnings.
- File-template errors, action/SGC-ID workflow errors, authorization failures,
  network/queue failures and general lifecycle notices are outside this
  record-validation fixture. They are not reproducible solely as record data.

Sources: `Submission::load_from_json()` and `initialize_submission_errors()`,
`DiseaseResolver`, `PmidNormalizer`, `SubmissionFileValidation`,
`SubmissionController::deprecatedDiseaseWarning()`,
`SubmissionDuplicateDetection`, and the submission/job Vue components.

## Verification

Checked the generated workbook with the application against the current local
database using a read-only database session and no external PMID fetches:

- Exactly 20 submission rows and 18 columns; template headers on row 6.
- Main sheet has warnings but no upload-blocking errors.
- Blocked sheet is rejected with the expected field and date-range reasons.
- All 14 non-fixture rows produce the expected error keys when passed to
  unsaved Submission objects as raw packets; R08 has all six PMID issues.
- Fixture prerequisites are documented, not installed or exercised against
  the local database. Actual browser upload/rendering was not performed.
